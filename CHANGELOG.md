# Changelog

Формат вдохновлён [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/). Записи — от новых к старым.

## [Unreleased]

### Added
- `scripts/lock-deps.sh` пересобирает lock-файлы зависимостей из `backend/requirements*.txt`
  через `uv pip compile`. Без `--upgrade` остальные версии не двигаются.
- Phase 13 — Hardening в `TASKS.md`: семь задач по приватности, воспроизводимой сборке и
  надёжности. Главная находка — pyannote по умолчанию шлёт телеметрию о каждой
  обработанной записи на `otel.pyannote.ai`.
- `TORCH_NUM_THREADS`: число потоков torch в worker, а через `OMP_NUM_THREADS` — и
  numpy/scipy. По умолчанию не задан. На Apple Silicon
  стоит попробовать число производительных ядер плюс пару (8 на M3 Pro с 11 vCPU): на всех
  ядрах распознавание в 1.5 раза медленнее.
- `ASR_BATCH_SIZE` (по умолчанию 8): сколько ASR-чанков распознаётся за один проход модели.
  На результат не влияет, только на скорость и память.
- `python -m benchmark.equivalence` сверяет оптимизированную диаризацию со стоковым pyannote
  на записи из `benchmark.run` и завершается с ненулевым кодом при расхождении. С
  `--only asr` — батчевое распознавание с прежним `transcribe()` по одному чанку.
- Phase 12 — Performance в `TASKS.md`: пять ускорений pipeline на CPU, ни одно не должно
  менять результат. Исходный замер: запись 37 мин обрабатывается 22 мин, из них ~70% —
  эмбеддинги спикеров в диаризации.

### Changed
- Образы ставят зависимости только из lock-файлов (`backend/requirements*.lock`) с
  проверкой хэшей. Раньше транзитивные зависимости не были закреплены, и чистая сборка
  брала свежие numpy, scipy и lightning, от которых зависит диаризация. Версии в lock — те
  же, что в образе, проверенном в Phase 12. torch-стек переехал в
  `backend/requirements-torch.txt`.
- Phase 12: запись 37 мин на CPU обрабатывается за 6 мин вместо 22 (M3 Pro, Docker,
  `TORCH_NUM_THREADS=8`). Транскрипт, таймкоды и спикеры совпали с прежними до слова.
- Worker загружает GigaAM при старте, а не в первой задаче. При первом запуске веса (428 МБ)
  скачиваются до того, как worker начнёт брать задачи. `start_period` healthcheck worker
  поднят с 300 до 600 с.
- Прогресс-бар двигается во время диаризации: pyannote отчитывается о каждом батче
  сегментации и эмбеддингов. Доли стадий пропорциональны измеренному времени — диаризация
  2–74%, распознавание 74–98%. Раньше бар большую часть задачи стоял на ~13%.
- Распознавание речи в 2.4 раза быстрее при том же результате: чанки GigaAM идут в модель
  батчами прямо из памяти, без временного WAV и без запуска ffmpeg на каждый чанк. На
  записи 37 мин — 294 с → 124 с, все 3967 слов и их таймкоды совпали.
- Диаризация в 3 раза быстрее при том же результате: эмбеддинги спикеров считаются одним
  проходом ResNet на окно, а не тремя. На записи 37 мин — 1014 с → 339 с, спикеры и
  сегменты совпали со стоковым pyannote точно.
- `pyannote.audio` закреплён точной версией `4.0.7`: ускорение заменяет его внутренний метод.
- Предупреждение «Worker недоступен» (на главной и на странице задачи) появляется только
  после двух ответов `/health` подряд. Одиночный сбой проверки больше не пугает текстом
  «задачу придётся запустить заново».
- `AGENTS.md`: раздел «Current assignment» отмечает T11.2 сделанным, появился раздел
  «Документация» со ссылками на `docs/` и `CHANGELOG.md`.
- Время обработки считает сервер: в ответе `Job` появились поля `processing_seconds` и
  `processing_includes_queue`. UI их больше не пересчитывает, поэтому определение одно
  и покрыто тестами. В Redis эти поля не пишутся.

### Fixed
- Удалённая задача больше не воскресает. Если удаление приходилось между чтением и записью
  статуса (worker обновляет его на каждом шаге прогресса), запись возвращалась со статусом
  выполняющейся задачи и без файлов. Теперь статус записывается, только если запись ещё есть.
- Recovery при старте worker больше не падает на задаче, которую удалили в этот момент.
- Сбой обновления прогресса во время диаризации (например, Redis на мгновение недоступен)
  больше не выдаётся за `DIARIZATION_FAILED`: исключение проходит как есть.
- Удалённая во время диаризации задача останавливается на ближайшем батче, а не после
  окончания всей диаризации.
- Страница задачи предупреждает, если worker недоступен, и останавливает счётчик «Идёт X».
  Раньше счётчик рос бесконечно и выдавал зависшую задачу за выполняющуюся, а
  предупреждение было только на главной странице.
  Вместо длительности выводится время последнего обновления. Цифра включала бы весь простой
  после краха и при опросе продолжала бы расти.
- Около паритета UI больше не пишет «быстрее записи в 1.0 раза» или «медленнее в 1.0 раза»,
  а пишет «примерно за длительность записи». Дробная часть выводится через запятую.
- Для задачи, упавшей из-за краха worker, UI пишет «Остановилась не раньше чем через X»:
  это оценка снизу (см. запись про recovery ниже).
- На странице задачи нет пустого абзаца, пока строке о времени нечего сказать (задача в
  очереди). Секундный таймер тоже не запускается, пока задача в очереди.
- Список задач помечает «(вместе с очередью)» время старых записей. Раньше эта пометка
  была только на странице задачи, и цифры в списке и на странице расходились по смыслу.
- Задача, которая упала ещё в очереди, больше не показывает «Остановилась через N ч —
  вместе с ожиданием в очереди». Время у неё неизвестно, поэтому строка не выводится.
- Счётчик «Идёт X» не зависит от расхождения часов браузера и сервера: браузер прибавляет
  к серверному значению только время, прошедшее с момента получения записи.
- Больше не бывает «обработка NaN с»: время приходит с сервера числом.
- Recovery больше не засчитывает простой worker во время обработки: у упавшей задачи
  `finished_at` теперь равен её последнему обновлению, а не моменту перезапуска worker.
  Подробности — [docs/processing-time.md](docs/processing-time.md).

### Security
- UI и API по умолчанию доступны только с этого компьютера: порты опубликованы на
  `127.0.0.1`, а не на всех интерфейсах. Раньше любой в той же сети мог открыть UI и
  скачать все транскрипты — авторизации у API нет. Доступ из сети включается сознательно:
  `BIND_ADDRESS=0.0.0.0` плюс адреса в `NEXT_PUBLIC_API_URL` и `CORS_ORIGINS`.
- pyannote больше не отправляет телеметрию. `pyannote.audio` 4 по умолчанию сообщал на
  `otel.pyannote.ai` о каждой загрузке моделей и о каждой обработанной записи: её
  длительность, число спикеров, версию и ID сессии. Аудио и текст не уходили.
  Worker выставляет `PYANNOTE_METRICS_ENABLED=false` перед загрузкой моделей, образ worker —
  тоже. `HF_HUB_DISABLE_TELEMETRY` теперь задаётся принудительно, а не только по умолчанию.
