# Время обработки задачи

Как считается и показывается «сколько заняла расшифровка» (T11.2).

## Отметки на записи задачи

| Поле | Когда ставится | Кто ставит |
|---|---|---|
| `created_at` | при загрузке файла | `JobStore.create` |
| `started_at` | при первом переходе в рабочий статус (не `QUEUED`, не терминальный) | `JobStore.update` |
| `finished_at` | при переходе в `COMPLETED` или `FAILED` | `JobStore.update` |
| `updated_at` | при любом изменении записи | `JobStore.update` / `replace` |

Отметки ставит только `JobStore.update`. Через него проходит каждая смена статуса,
поэтому ни один путь кода не может забыть поставить отметку.

## Где считается время: только на сервере

`Job` отдаёт два вычисляемых поля (`@computed_field` в `app/schemas/job.py`):

| Состояние записи | `processing_seconds` | `processing_includes_queue` |
|---|---|---|
| `QUEUED`, worker ещё не взял | `null` | `false` |
| выполняется (`started_at` есть, `finished_at` нет) | `now − started_at` по часам сервера | `false` |
| завершена (`started_at` и `finished_at` есть) | `finished_at − started_at` | `false` |
| упала, не начавшись (`finished_at` есть, `started_at` нет) | `null` | `false` |
| старая запись: терминальная, обеих отметок нет | `updated_at − created_at` | `true` |

Раньше UI считал время сам, и определения разошлись: задачу, упавшую ещё в очереди, бэкенд
считал «время неизвестно», а UI показывал `created → updated` с пометкой про очередь. Теперь
определение одно, и тесты проверяют именно то, что видит пользователь.

В Redis эти поля не пишутся (`DERIVED_FIELDS` в `JobStore._persist`), иначе у выполняющейся
задачи там лежало бы устаревшее значение. Они вычисляются при каждой сериализации: в ответе
API, в каждом SSE-событии и в pub/sub-сообщении.

## Где показывается

- Страница задачи (`JobProgress`): «Идёт X» во время работы, «Расшифровка заняла X — быстрее
  записи в N раза» или «Остановилась через X» в конце. Если `processing_includes_queue`, то
  вместо сравнения с записью — «вместе с ожиданием в очереди». Пока задача в очереди, строки
  нет совсем, и секундный таймер не тикает.
  - Сравнение с записью округляется до десятых **один раз**. Если вышло ≤ 1,0, UI пишет
    «примерно за длительность записи»: иначе 290 с и 310 с на 300-секундной записи дали бы
    противоречивые «быстрее в 1,0 раза» и «медленнее в 1,0 раза».
  - Для `WORKER_CRASHED` — «Остановилась не раньше чем через X»: см. раздел про recovery.
- Список задач (`JobList`): «обработка X», для старых записей «обработка X (вместе с
  очередью)». Пометка обязательна в обоих местах, иначе одна и та же цифра читается по-разному.
  У выполняющейся задачи цифра обновляется вместе с опросом списка (раз в 5 с) и берётся с
  сервера как есть. Признака мёртвого worker в списке нет, его показывает баннер на главной
  странице.

## Счётчик «Идёт X» и часы браузера

Если вычитать серверный `started_at` из `Date.now()` браузера, расхождение часов попадает
прямо в счётчик. После сна хоста VM Docker Desktop/WSL2 может отставать или спешить на
минуты, UI могут открыть и с другой машины в LAN. При отстающем браузере счётчик зависал
на «0 с», при спешащем время раздувалось.

Сейчас браузер берёт `processing_seconds` с сервера и прибавляет только время, прошедшее с
получения записи (`receivedAt` в `useJob`). Обе эти отметки сняты по часам браузера, так
что расхождение с сервером сокращается. Остаются мелкие погрешности: задержка доставки (на
fallback-ветке SSE — до `SSE_POLL_SECONDS`) и разница часов контейнеров API и worker,
которые на одном хосте совпадают.

## Мёртвый worker

Статус задачи не меняется, когда worker умирает: запись остаётся в `DIARIZING` до
следующего старта worker, на котором её подхватит recovery. Если в это время показывать
растущий счётчик «Идёт 3 ч 41 мин», зависшая задача выглядит активной, а сам счётчик
утверждает, что всё в порядке.

Поэтому `JobView` опрашивает `/health` (как главная страница), а `JobProgress` при
`workers.status !== "ok"` для незавершённой задачи:

- показывает предупреждение. Для задачи в очереди: «начнётся, когда worker вернётся». Для
  начатой: «после перезапуска будет помечена как прерванная», потому что именно это
  сделает recovery;
- останавливает секундный таймер и вместо «Идёт X» пишет «Последнее обновление в ДД.ММ ЧЧ:ММ:
  worker недоступен».

Длительность для такой задачи не показывается. Сервер считает её до «сейчас», поэтому
если открыть страницу через 9 часов после краха, получилось бы «после 9 ч». Кроме того,
при работе через опрос (SSE недоступен) каждый ответ приносил бы новое «сейчас», и цифра
росла бы при остановленном таймере. `updated_at` — серверная отметка, она не зависит ни от
момента запроса, ни от часов браузера.

Предупреждение появляется только после **двух ответов `/health` подряд** со статусом worker
не `ok` (`workersDown` в `useHealth`, общий для главной страницы и страницы задачи). Одиночный
`down` бывает ложным: Redis на мгновение не ответил, поток heartbeat опоздал. А текст
предупреждения велит перезапускать задачу. Цена — до 10 с (один интервал опроса) лишней
задержки, прежде чем UI сообщит о реально умершем worker. Панель «Состояние системы»
по-прежнему показывает сырой статус каждого ответа: это диагностика, а не вывод.

Признак берётся из `/health`, а не по тому, как давно не было событий: тишина в SSE ничего
не значит. С T12.4 диаризация обновляет задачу примерно на каждый процент бара, но паузы
между событиями всё равно зависят от длины записи и скорости машины, а кластеризация в конце
стадии идёт совсем без них. `/health` уже учитывает `last_heartbeat` (см. AGENTS.md,
«Мёртвый worker не считается живым…»).

## Задачи, которые восстановила recovery

`recover_orphaned_jobs` узнаёт о крахе только при следующем старте worker, а это может
случиться через несколько часов после падения. Если бы `finished_at` ставился на момент
старта, весь простой контейнера попал бы во «время обработки».

Поэтому recovery передаёт в `store.fail(..., finished_at=job.updated_at)` время последнего
обновления задачи. Это последний момент, когда задача заведомо была жива, так что время
обработки у такой задачи — **оценка снизу**. Реальный крах мог случиться позже на длину
самой долгой паузы между обновлениями. До T12.4 это было до ~20 минут: диаризация шла без
промежуточного прогресса. Теперь это секунды: обновление приходит примерно на каждый
процент бара, дольше всего молчит кластеризация в конце диаризации.

`updated_at` при этом всё равно ставится на момент recovery: сама запись была изменена
именно тогда.

### Старая запись, зависшая в рабочем статусе

Запись, созданная до появления `started_at`, могла остаться в рабочем статусе (например,
`DIARIZING`). После recovery у неё есть `finished_at`, но нет `started_at`, и она попадает
в ветку «упала, не начавшись»: `processing_seconds = null`. Запасной расчёт
`created_at → updated_at` к ней сознательно не применяется. `updated_at` у такой записи —
момент recovery, поэтому цифра включила бы весь простой между крахом и перезапуском.
Показать «время неизвестно» честнее, чем показать неверное. Такие записи остались только
от версий до T11.2.
